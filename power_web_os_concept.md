# 1. Варианты elevator pitch

## 1.1. Основной вариант

**Power Web OS — это платформа для сложных B2B-продаж, которая помогает компаниям находить не просто лиды, а реальные маршруты входа в целевые аккаунты. # 2. Детальная концепция продукта

## 2.1. Рабочее название

**Power Web OS**

Альтернативные названия:

- **Account Access Planner**
- **Power Web Intelligence**
- **ABM Game Engine**
- **Access Planning Platform**
- **Signal-to-Access OS**

Лучшее позиционирование на текущем этапе:

> **Power Web OS — white-box платформа для сложных B2B-продаж, которая находит сигналы спроса, строит динамическую карту влияния в аккаунте и предлагает объяснимые маршруты доступа к buying committee.**

---

## 2.2. Центральная идея

Продукт не продаёт “базы ЛПР” и не автоматизирует серый outreach.

Он решает другую задачу:

> **Помочь B2B sales-команде понять, какие аккаунты сейчас стоит брать в работу, кто реально влияет на решение, через какие легальные и допустимые маршруты можно выйти на Power Web, и какой следующий ход нужно сделать.**

Ключевая формула:

```text
Сигнал без маршрута = аналитика.
Маршрут без сигнала = спам.
Сигнал + Power Web + Access Plan + допустимый ход = продаваемый продукт.
```

---

## 2.3. Почему это нужно рынку

В сложных B2B-продажах покупка редко принимается одним человеком. Обычно решение формируется сетью внутренних и внешних участников: бизнес-заказчиков, технических экспертов, закупщиков, финансистов, юристов, службы безопасности, внешних консультантов, интеграторов и текущих поставщиков.

Одновременно прямой outreach становится менее эффективным: покупатели избегают нерелевантных сообщений, а sales-команды всё чаще сталкиваются с тем, что “нашли контакт, написали, не получили ответа”.

Значит, выигрывает не тот, кто “нашёл email директора”, а тот, кто понимает:

```text
почему аккаунт актуален сейчас;
кто внутри и снаружи влияет на покупку;
какой маршрут доступа уместен;
какой ход не выглядит спамом;
какой следующий шаг меняет конфигурацию сделки.
```

Для первого слайда презентации можно использовать следующие источники:

- Forrester: в типичной B2B-покупке участвуют 13 внутренних стейкхолдеров и 9 внешних влияющих лиц.  
  Источник: https://www.forrester.com/press-newsroom/forrester-2026-the-state-of-business-buying/

- Gartner: 73% B2B-покупателей активно избегают поставщиков, которые присылают нерелевантные сообщения.  
  Источник: https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-sales-survey-finds-61-percent-of-b2b-buyers-prefer-a-rep-free-buying-experience

## 2.6. Главная боль

Сегодня sales-команда часто работает так:

```text
нашли компанию → нашли контакт → написали → ждём → не ответил → следующий контакт
```

Но в enterprise B2B проблема обычно не в отсутствии контакта. Проблема в том, что команда не знает:

- есть ли у аккаунта реальный актуальный триггер;
- кто economic buyer;
- кто technical buyer;
- кто может стать champion;
- кто blocker;
- кто текущий поставщик;
- кто внешний инфлюенсер;
- есть ли закупочный процесс;
- через кого лучше заходить;
- что нельзя делать по правилам компании;
- какой следующий ход повышает вероятность сделки.

---

## 2.7. Продуктовая философия

### Не чёрный ящик

Access Plan не должен выглядеть так:

```text
ИИ рекомендует написать CIO.
```

Он должен выглядеть так:

```text
Рекомендуемый ход: пригласить Head of Data на закрытый technical benchmark.

Почему:
+ найден свежий hiring signal по Data Engineers и DWH Architect;
+ Head of Data публично выступал по теме аналитики;
+ в playbook клиента разрешены экспертные мероприятия;
+ прямой cold Telegram запрещён;
+ economic buyer пока не проявлен, поэтому сначала нужен technical champion.

Ожидаемое изменение состояния:
Head of Data: identified → engaged / champion_candidate.
```

### Human-in-the-loop

ИИ не должен сам писать ЛПР и вести сделку. Он должен помогать:

- находить сигналы;
- строить гипотезы;
- предлагать маршруты доступа;
- объяснять рекомендации;
- готовить черновики сообщений;
- классифицировать ответы;
- обновлять состояние Power Web.

Но отправка, коммуникация и коммерческое решение остаются за человеком.

Метафора продукта:

> **Клиент задаёт правила игры. Система видит доску. ИИ предлагает допустимые ходы. Человек утверждает и исполняет. Результат хода меняет состояние доски.**

| Элемент | В продукте |

## 2.9. Основные модули продукта

- ICP fit score;
- intent score;

Источники:

- ФНС / СПАРК / Контур / DaData;

- HH и вакансии;

- новости;

- отраслевые медиа;
- корпоративные Telegram-каналы;
- CRM клиента;
- мероприятия и конференции.

HH здесь особенно ценен не как источник контактов, а как источник account intent: вакансии показывают рост функций, стек, географию найма и организационные приоритеты.

### Модуль 2. Power Web

Отвечает на вопрос:

> **Кто влияет на решение и в каком состоянии находится наша позиция в аккаунте?**

Power Web включает:

- внутренние роли;
- найденных людей;
- внешних инфлюенсеров;
- интеграторов;
- текущих поставщиков;
- конкурентов;
- procurement;
- legal/security gatekeepers;
- возможных champions;
- blockers;
- неизвестные, но необходимые роли.

Пример состояний:

| State | Значение |
|---|---|
| `missing` | Роль нужна, но человек не найден |
| `suspected` | Есть гипотеза, кто это |
| `identified` | Человек найден и подтверждён источником |
| `reachable` | Есть допустимый канал |
| `contacted` | Был контакт |
| `engaged` | Ответил / проявил интерес |
| `champion_candidate` | Может стать проводником |
| `champion` | Активно помогает |
| `neutral` | Знает о нас, но не двигает сделку |
| `blocker` | Мешает продвижению |
| `competitor_aligned` | Связан с конкурентом |
| `no_go` | Нельзя использовать / высокий риск |

### Модуль 3. Sales Playbook Configurator

Отвечает на вопрос:

> **По каким правилам эта компания играет в продажи?**

Это white-box конфигуратор. Он задаёт не промпт, а правила.

Что конфигурируется:

| Блок | Пример |
|---|---|
| ICP | Отрасли, размер, регионы, исключения |
| Buying committee | CDTO, CIO, CISO, Procurement, Integrator |
| Signals | Hiring, закупки, смена руководства, мероприятия |
| Allowed moves | Вебинары, partner intro, executive briefing |
| Forbidden moves | Холодный Telegram, звонки через секретаря |
| Channels | Email, LinkedIn manual, партнёр, event, CRM |
| Assets | Кейсы, white papers, исследования, вебинары |
| Geo constraints | Только Москва/СПб, без регионального офлайна |
| Compliance rules | Где нужен review, где нельзя автоматизировать |
| Competitors | Кого отслеживать, чем бить |
| Success criteria | Meeting, reply, intro, RFP, pilot |

Пример правила:

```yaml
if:
  signals:
    - data_team_growth
    - digital_transformation
  missing_roles:
    - CDTO
  assets_available:
    - data_benchmark
  channels_allowed:
    - event_invitation
then:
  recommend_move: invite_to_closed_benchmark
  priority: high
  owner: marketing
  expected_state_change:
    role: CDTO
    from: missing
    to: identified_or_engaged
```

### Модуль 4. Access Planner

Отвечает на вопрос:

> **Какой следующий ход лучше сделать по этому аккаунту?**

Access Planner оценивает маршруты не “по мнению ИИ”, а по объяснимой формуле.

```text
Access Route Score =
  Trigger Fit
+ Role Leverage
+ Evidence Strength
+ Channel Availability
+ Relationship Strength
+ Asset Match
+ Timing
+ Playbook Priority
- Compliance Risk
- Reputation Risk
- Cost / Effort
- Latency
```

Пример output:

```text
Top move: Partner Intro через интегратора X

Score: 84 / 100

Почему:
+ интегратор X уже работал с этим аккаунтом;
+ у клиента есть партнёрская связь с X;
+ прямой CDTO не найден;
+ hiring signal подтверждает data-проект;
+ playbook разрешает partner-led motion;
- риск: интегратор может быть связан с конкурентом.

Следующее действие:
Partner Manager → запросить intro к Head of Data или CDTO.
```

- source;
- URL;
- timestamp;
- confidence;
- data type;

- allowed usage;
- restrictions;
- audit trail.

```json
    "telegram": "not_allowed",

```

## 2.22. Короткое финальное описание продукта

**Power Web OS** — это white-box платформа для B2B sales и ABM-команд, которая собирает публичные и first-party сигналы по целевым аккаунтам, строит динамическую карту buying committee и внешней экосистемы, а затем предлагает объяснимые Access Plans: через кого, каким маршрутом, с каким поводом и каким следующим ходом выходить на Power Web.

На этой основе продукт оценивает состояние аккаунта, выявляет недостающие фигуры, предлагает top-3 маршрута доступа и создаёт задачи для sales, marketing, partner manager или RevOps.

Главная ценность:

> **Продукт превращает account intelligence в управляемую стратегию доступа к сделке.**

# 3. Структура презентации для команды стартапа

## Слайд 1. Почему проблема стала острой

### Цель слайда

Показать команде, что проблема не выдумана: изменилась сама природа B2B-покупки и эффективность старых инструментов снижается.

### Тезисы

- B2B-покупка стала коллективной: в среднем 13 внутренних участников и 9 внешних влияющих лиц.
- Покупатели избегают нерелевантного outreach: 73% активно избегают поставщиков с нерелевантными сообщениями.
- Значит, проблема не в “найти контакт”, а в “понять сеть влияния и правильный маршрут входа”.

## Слайд 2. Элеватор-питч

**Power Web OS — это платформа для сложных B2B-продаж, которая помогает компаниям находить не просто лиды, а реальные маршруты входа в целевые аккаунты. Мы собираем публичные и внутренние сигналы по компаниям, определяем, почему аккаунт может быть актуален сейчас, строим Power Web — карту людей, ролей и внешних влияющих игроков вокруг сделки — и формируем Access Plan: объяснимый план доступа к аккаунту, где указано, кого искать, через какой маршрут заходить, какой повод использовать и какой следующий ход сделать.**

**Это не база контактов и не рассыльщик. Это стратегический слой между рыночной аналитикой и CRM, который помогает sales-команде понять, как практически зайти в сложную сделку.**

## Слайд 4. Новый подход: не контакты, а доступ

- Access Plan отвечает: **как зайти**.
- Playbook отвечает: **какие ходы допустимы**.
- CRM фиксирует: **что было сделано и какой результат**.

- какой следующий шаг;
- кто владелец действия;
- какое изменение состояния ожидается.

---

## Слайд 10. White-box принцип

### Система не говорит

```text
“ИИ решил”.
```

### Система показывает

- какой сигнал найден;
- какая роль важна;
- какое правило продаж сработало;
- какие ходы разрешены;
- какие запрещены;
- какой ожидаемый результат хода;
- где нужен ручной review.

### Главный тезис

> Access Plan = правила продаж × состояние Power Web × сигналы аккаунта × доступные активы × CRM-контекст.

## Слайд 12. MVP и следующий шаг

### MVP

- 1–2 playbook-шаблона;
- 50–100 аккаунтов;
- сигналы по аккаунтам;
- Power Web Lite;
- Access Plan по ключевым аккаунтам;
- экспорт задач в CRM.

### Цель пилота

> **Доказать, что продукт не просто находит данные, а помогает sales-команде делать более точные ходы по стратегическим аккаунтам.**

### Критерии проверки MVP

- sales подтвердил релевантность аккаунтов;
- sales понял, что делать дальше;
- Access Plan привёл к конкретным действиям;
- появились встречи / ответы / интро / новые stakeholders;
- команда готова использовать продукт повторно.
